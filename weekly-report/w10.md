## Completed

### CKBuilder — Deploy Script: Type ID code hash correction

- **The bug**: the deploy page showed the Type ID **args** under the label "Code Hash
  (Type ID)". A script is identified by `blake2b(code_hash ‖ hash_type ‖ args)`, so the
  bare args reference a script that does not exist — anyone copying that value out of the
  UI got a reference that could never resolve.
- **The fix**: `buildDeployTx` now also returns `typeIdCodeHash = tx.outputs[0].type.hash()`
  (`ckb-lab/app/lib/ckb/deploy.ts`), and the preview card shows the two values as separate
  rows — "Type ID args" and "Code Hash (Type ID)" — with the code hash marked as the one to
  copy. `docs/deploy-features.md` gained a table documenting the distinction.

### CKBuilder — Invoke Script page (Course 07) — built, not yet pushed

- **What it does**: builds a transaction that exercises a deployed script as a **type
  script** — attaches it to `outputs[0].type`, adds the deployed cell as a `dep_type:
  "code"` cell dep, signs and broadcasts, then reports whether the node accepted it through
  the full lifecycle banner (`sending → sent → pending → proposed → committed`, or
  `rejected` carrying the node's own reason).
- **Deployed-script registry**: `/deploy` produced a code hash and an outpoint with nowhere
  to put them, so using a freshly deployed script meant copying both by hand. Committed
  deploys are now recorded in `localStorage` (`lib/ckb/deployed-scripts.ts`), network-scoped
  and filtered on read, and offered on `/invoke` as a dropdown with `hash_type` prefilled
  from how the script was actually deployed.
- **Witness placement**: the payload goes into `WitnessArgs.outputType`, not `witnesses[0]`
  as raw bytes. Input 0 belongs to the signer, so its secp256k1 signature owns
  `witnesses[0]` and raw hex written there is silently overwritten by `signTransaction`.
- **Capacity**: output capacity is left at 0 and computed by `completeInputsByCapacity` from
  the real lock + type + data bytes — a hardcoded formula would be wrong for any wallet
  whose lock args are not the 20-byte secp256k1 default. Attached capacity is applied
  *before* `completeFeeBy`, which is what tops up the resulting shortfall.
- **Scope held deliberately**: the **Lock** path needs two transactions and is deferred to
  Course 08 (issue #6), where a hash lock gives the witness something real to prove. The
  action registry (`lib/ckb/script-actions.ts`) ships **empty** — CKB has no ABI, so an
  action list can never be derived from a `code_hash` alone, and inventing entries for
  scripts that do not exist would be fiction. Course 10 (issue #8) registers the first real
  one.
- **Spec written** as `docs/invoke-features.md`: lock-vs-type comparison, witness placement,
  cell deps, capacity, every UI state, and edge cases.

## Key Learnings

### A script is identified by all three of its fields
The Type ID bug came from treating the args as the identifier. Because a script is
`blake2b(code_hash ‖ hash_type ‖ args)`, a value that *looks* like a hash is not
automatically the hash that resolves. What made it costly is where the failure surfaces —
at cell-dep resolution during broadcast, far from the UI that handed over the wrong value,
and with an error message that describes the symptom rather than the cause.

### You do not call a CKB script
There is no entry point, no function selector, no return value to read — a script is a
RISC-V binary that receives the whole transaction and returns 0 or non-zero. So "invoking"
one means constructing a transaction that gives it a reason to run and observing whether the
node accepts it. That reframing changed the page's design: a rejection is a first-class
outcome that displays the node's own reason, not an error state to hide.

### Process cost has to be scoped like a feature
The uniform Definition of Done was correct per-page and wrong in aggregate — 24 courses
multiplied by the full polished artifact set simply did not fit the window. Tiering it, and
threading the tier through the automation so the split wasn't cosmetic, was cheaper than
either dropping the gates or dropping the courses. Worth noticing that the constraint only
became visible once the whole roadmap existed as issues and could be counted.

### Scope against what the data can actually support
Scoping FiberGate v2 against the real schema killed several plausible-sounding features
before they became issues: a liquidity trend chart with no history table behind it, an
expirations-per-day chart that could only bucket by the wrong timestamp, a network-capacity
gauge with no denominator anywhere. Writing those findings into the epic rather than just
omitting the features means the next person picking up a sub-issue does not rediscover them
halfway through building.
