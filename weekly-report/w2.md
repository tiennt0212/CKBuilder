## Key Learnings
### Core Structure
1. Script
Compare Script and Code:
- Script is a data structure referencing to runnable on-chain code.
- Code refers to the RISC-V binary, runnable in CKB-VM and can be referenced to by the Script structure.
- A code Cell is a Cell containing RISC-V binary code.
- Script does not directly include code; it simply stores a pointer to reference the code.

- Lock Script is a specific script that determines the ownership of a Cell. 

2. Transaction
- A transaction in CKB destroys some Cells (outputs from pre-transactions) and generates new ones.
- Transaction Life cycle:
  - Pending:
    - the generator store pending transactions locally and send them to CKB nodes.
    - We shouldn't use the pending transactions output Cells unless the transaction is stuck or requires a fee bumping.
  - Confirming:
    - once the transaction appears in a block on the canonical chain.
    - Although existing on the canonical chain, it still not quanlified as "Confirmed".
    - Same as Pending transaction, the Confirming one is not recommended to use the output Cells of Confirming transactions
    - The block containing the transaction gives one confirmation. Each descendant block in the chain gives an extra confirmation.
  - Confirmed:
    - The "Confirming" transaction becomes Confirmed when it has received at least X confirmations.
    - The generator can freely use the out put Cells of confirmed transactions
  - Conflicting:
    - 2 different txs conflict when:
      - Tx conflict input Cells with another one, or any ancestor of another one.
      - They are descendants of a pair of conflict txs.
    - The generator should not use the output Cells of conflicting txs, because there's a chance they may become Pending again (when the block contains the conflicting tx have been reverted, the conflicting tx revert to Pending).
    - generator shouldn't use the output cells of conflicting txs.
    - If any conflicting txs received X confirmations, the conflicting txs become Conflicted
  - Conflictive:
    - when it conflicts with an on-chain tx that has received at least X confirmations.
    - The generator shouldn't use the output Cells of conflictive transactions.
    - If all blocks contains conflitive txs have been reverted, the conflictive txs revert to Pending.
  - Reverted: if a chain reorganization reverts the block containing the transaction, the transaction becomes Reverted.
  - Abandoned:
    - User or Apps can mark a pending transaction as Abandoned, if they decide to give up a stuck transaction.
    - However, due to a tmiing gap, an abandoned tx may still be already submitted to a node.
    - Txs can be transformed from Abandoned to Pending, or Confirming, or Conflicting
