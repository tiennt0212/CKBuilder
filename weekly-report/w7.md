## Key Learnings
### Transfer Feature Architecture
- **Component split**: Separating `TransferInputCard` from `TransferPreviewCard` keeps the form input stateless and the preview read-only, making each independently testable and easier to reason about.
- **Debounced preview**: Triggering a preview build on every keystroke floods the RPC. A debounced `onValuesChange` handler — with an in-progress guard to skip rebuilds mid-transfer — solves this cleanly.
- **Zombie state prevention**: `useTransfer` increments a generation counter on every `reset()`. The async poll callback checks if its generation still matches before writing state, preventing stale updates from a cancelled flow from landing in the UI.

### feeRate and `completeFeeBy`
- **Unit**: feeRate is in **shannons/KB** (not shannons/byte). CKB Lab uses three presets: `1000` (Slow), `2000` (Standard), `5000` (Fast).
- **Passing it in**: `tx.completeFeeBy(signer, feeRate?)` — the `feeRate` argument is optional. Omitting it lets CCC fetch the current rate from the node via `getFeeRateStatistics`. Pass it explicitly to override.
- **Call order**: `completeFeeBy` must be called **after** all outputs have been added — it performs coin selection, calculates the fee, and appends the change output in a single call.
- **Reading the fee after build**: After `completeFeeBy` completes, call `tx.getFee(signer.client)` to get the actual fee as a bigint (in shannons) to display in the preview panel before the user signs.

### buildTx before sending (preview flow)
- **`buildOnly` pattern**: `useTransfer.transfer({ buildOnly: true })` runs through the full build + fee calculation step but does **not** sign or broadcast. The hook returns to `Idle` afterward. Used to populate the `SummaryPanel` (amount, fee, recipient) without opening the wallet popup.
- **Two call sites for `buildTx`**: `TransferForm` triggers a debounced `buildTx` on every form change (to keep the preview fee fresh), and triggers `transfer()` on submit (to actually sign and send). The hook does not cache the built tx — it rebuilds each time to ensure the fee is calculated against the latest UTXO set.
- **In-progress guard**: `onValuesChange` checks `isInProgress` before triggering a preview rebuild — prevents rebuilding the tx mid-flight while the user is already in the signing or sending step.

### Transaction state handling
- **State machine**: `idle → building → signing → sending → sent → pending → proposed → committed / rejected / error`. The `sent/pending/proposed` states are node-reported and updated via a poll loop every 2 seconds.
- **Generation counter (zombie guard)**: Every `reset()` increments `transferId.current`. Every `await` inside `transfer()` checks `if (myId !== transferId.current) return` — if the user resets mid-flight, stale async results are discarded and never written to state.
- **Poll cancellation**: In addition to the generation counter (which guards the main flow), the poll loop uses a separate `pollSignal = { cancelled: false }` object. `reset()` sets `signal.cancelled = true`; the `while (!signal.cancelled)` loop exits on the next iteration.
- **RPC retry in poll**: The poll loop tracks `rpcErrors` independently. Transient RPC failures (network blip) do not terminate the loop immediately — it only terminates after 3 consecutive errors, avoiding false error states when the node is momentarily unreachable.
- **Stale state clear on reset**: `reset()` clears `txHash`, `blockNumber`, and `fee` back to `null` — prevents the `SummaryPanel` from showing the previous transfer's fee while a new one is being built.

### Cell Query with `findCellsPaged`
- **Primary script**: `findCellsPaged` takes a single script as the anchor. If querying by lock (address) → `scriptType: "lock"`. If querying by type script alone → `scriptType: "type"`. Both cannot be primary at the same time.
- **Combining lock + type**: When both are present, lock is primary and the type script goes into `filter.script`. The CKB Indexer filters by type server-side after querying by lock — avoids pulling all cells to the client for filtering.
- **`scriptSearchMode: "exact"`**: Use `"exact"` to match the full `codeHash + hashType + args`. Use `"prefix"` to match any cell whose args starts with the given value — useful for querying multiple args in one call.
- **Range filters are `[min, max)` exclusive**: `outputCapacityRange` and `outputDataLenRange` use a half-open interval. To get an inclusive upper bound, add `1n` to the max when building the filter.
- **`getCellsCapacity` for totals**: Run `findCellsPaged` and `getCellsCapacity` in parallel with the same searchKey — the latter returns the total capacity across **all pages** without fetching the cells, used to populate the stats bar.
- **`dataSearchMode`**: Supports `"prefix"` (hex starts with pattern), `"exact"` (full match), and `"partial"` (contains pattern anywhere). Defaulting to `"prefix"` is the safest general choice.

### Hash Lock Script (Lesson 08)
- **`#![no_std]` + CKB-VM**: CKB scripts compile to RISC-V ELF and run inside CKB-VM, a bare-metal sandbox with no OS. `#![no_std]` drops the standard library; `ckb-std` provides CKB syscalls, a simple allocator, and blake2b.
- **`load_script()` vs `load_witness()`**: `load_script()` returns the executing script (including `args` — here, the expected hash). `load_witness(0, Source::GroupInput)` returns the first witness for the current script group, which the spender populates with the preimage.
- **`Source::GroupInput`**: When multiple inputs share the same lock script, CKB runs the script once for the group. `GroupInput` indexes within that group, so the script is agnostic to where in the transaction its input appears.
- **Error codes**: CKB uses exit code 0 for success and non-zero for failure. Named constants (`ERROR_INVALID_ARGS_LENGTH = 5`, `ERROR_NO_WITNESS = 6`, `ERROR_EMPTY_PREIMAGE = 7`, `ERROR_HASH_MISMATCH = 8`) make failed transactions debuggable without inspecting VM internals.
- **Off-chain ↔ on-chain hash parity**: Both sides must use `blake2b` with personalization `"ckb-default-hash"`. Using `ccc.HasherCkb` off-chain guarantees this automatically — no manual configuration needed.
- **Deploy lifecycle**: Scripts are deployed as ordinary cell data. Transactions that use the script must reference the code cell via `cell_deps` with `dep_type: "code"`. The `code_hash` in the lock script equals `blake2b(binary)` when `hash_type = "data1"`.
