## Completed

### CKBuilder — PR #35 merged: Invoke Script page + deploy fix + Script Registry (closes the M2 deploy → invoke loop)

Three commits, one PR, merged to `canary`. Covers the Invoke Script build that last week's
report described as local-only, plus two follow-ons that grew out of debugging it.

- **`/invoke` (Type path)** — attaches a deployed script to `outputs[0].type`, adds the
  deployed cell as a `dep_type: "code"` cell dep, signs and broadcasts, and reports the
  node's verdict through the full lifecycle banner. A rejection (script returns non-zero)
  is a first-class outcome, not an error state — there is no way to "call" a CKB script, so
  the page's job is to construct a transaction that gives it a reason to run and show what
  the node decided.
- **Deploy bug fix — `hash_type` coupled to Type ID.** `hash_type` and the Type ID toggle
  were independent controls, so a plain data cell could be recorded with `hash_type: "type"`
  — a pair that never resolves and fails at `/invoke` as `ScriptNotFound`, far from where the
  bad value was chosen. Fixed: Type ID off restricts the choice to `data1`/`data2`; on forces
  `type`. The Type ID toggle now sits above Hash Type since it gates the options, and the
  deployed-script registry rejects the impossible pair on write.
- **Script source: Deployed vs Manual.** `/invoke` gained a segmented selector. Deployed
  reads `(code_hash, hash_type, outpoint)` from the registry and locks `hash_type` read-only
  — it's a property of how the script was actually deployed, not a free choice, which removes
  the trap of picking a value that yields `ScriptNotFound`. Manual accepts all fields by
  hand, including legacy `data` (VM0) and `dep_group`, for scripts this browser never
  deployed — with a "Save to registry" action that opens the registry drawer prefilled.
- **Shared constants.** `HashType` / `DepType` / `ScriptSource` object-namespaces moved into
  `lib/ckb/`, replacing magic strings scattered across Deploy, Invoke, and the cell-explorer
  type-script presets. The wire type stays `ccc.HashType` / `ccc.DepType`; only the JS-side
  namespace is new.
- **`/registry` — Script Registry page.** A CRUD management UI for the deployed-script
  registry that `/deploy` and `/invoke` share: table, view/add/edit/delete, and a per-entry
  Hidden toggle so a parked entry drops out of the `/invoke` picker without being deleted.
  Editing an identity field (`txHash`/`index`/`code_hash`) re-keys the entry (delete old id,
  write new) rather than duplicating it.
- **Architecture** — per `frontend-exp` → state-singleton-stores: `lib/ckb/deployed-scripts.ts`
  stays a pure `localStorage` layer; a new Zustand singleton (`stores/deployed-scripts.ts`)
  mirrors it and writes through on every mutation. `/deploy`, `/invoke`, `/registry` all read
  the one store instance, so a save on any page shows on the others with no reload — no class,
  since a class doesn't integrate with React's render cycle and would need wrapping in state
  anyway.
- **DoD status is intentionally incomplete.** `pnpm build`/`lint`/`tsc` pass, routes are
  registered, and `docs/invoke-features.md` + `docs/registry-features.md` +
  `docs/deploy-features.md` are updated — but the Claude Design artboard (gate 9, for Invoke
  manual mode + the new Registry screen) is deferred and batched into one pass rather than
  drawn twice, and end-to-end wallet testing is still pending (verified via build/lint/
  typecheck only so far). Recorded in the PR body rather than glossed over, since Course 07
  (issue #5) is `polished`-tier and both gates are still owed before it can close.

### CKBuilder — real-world testing surfaced a genuine CKB-VM gotcha, filed as issue #34

While wiring the existing `lesson-08-hash-lock` Rust contract (built back in June, sitting
unused at `contracts/lesson-08-hash-lock/`) through `/invoke`'s new Manual mode as a
dry run ahead of Course 08, the binary failed with a cryptic `VM Internal Error:
InvalidInstruction` on every `hash_type`. Root cause: it was built for `riscv64imac`, which
can still emit native atomic instructions (LR/SC/AMO) — and CKB-VM does not execute atomics
on *any* VM version, so no `hash_type` choice fixes it; the binary itself needs rebuilding
with `-C target-feature=-a`. Filed as **#34** — deploy-time ELF `.riscv.attributes` parsing to
catch this (and the related B-extension → `hash_type: data2` requirement) before it reaches
`/invoke` as an unexplained runtime error. Left open, not built — it's a Deploy-page
enhancement, orthogonal to Course 07/08.

## Key Learnings

### "Not yet pushed" and "shipped" can both undersell the actual gap
Last week's report flagged the Invoke work as local-only; this week it merged in three
commits and closed the deploy→invoke loop. But the PR itself records two gates still owed
(artboard sync, wallet testing) rather than checking every box to call it done — which means
"merged" isn't the same claim as "Course 07 is closed." Writing the gap into the PR body
where the next read of it will actually land is what made it visible instead of assumed away.

### A page-level bug fix and a contract-level bug look identical from the UI
Both the `hash_type`/Type-ID coupling bug and the `lesson-08-hash-lock` atomics failure
surface as the same class of downstream error — `ScriptNotFound` / `InvalidInstruction` far
from the actual mistake. One was fixed in the form (couple the controls, guard the registry);
the other can't be fixed in the form at all — the binary itself needs rebuilding, so the
right response was a deploy-time detector (#34), not a UI change. Worth checking which layer
a "the script isn't resolving" error actually belongs to before reaching for a form fix.

### A shared store turns three pages into one invariant to maintain
Before the Zustand singleton, `/deploy` and `/invoke` each had their own read path into the
same `localStorage` key, and `/registry` would have needed a third. Any registry bug fix
(the impossible hash_type/Type-ID pair, the re-key-on-edit behavior) now lives once in the
store instead of needing to be replicated per page that touches it.
