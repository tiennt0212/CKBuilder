## Key Learnings

### Basic technology concepts and terminology
- CKB stands for Common Knowledge Base
- Cell in CKB looks like a UTXO in Bitcoin. But it's even a higher level
    - In a cell, we can store any data, and script(s).
    - Cell has its own capacity. Capacity unit is CKB. 1 CKB = 10^8 Shannons.
    - When consuming a cell, the old cell will be expired, and the new cell(s) will be spawn. (looks like UTXO in Bitcoin)
- In CKB, data like CKB, NFT, FT (UTXO),... were stored on chain, not in smart contract state. 

### Scripts
- "lock" scripts manage the ownership for a cell: "who is able to spend this cell?", "any requirements to spend this cell?",
- Cell can refer to a script on CKB-VM through code_hash (looks like the hex code was returned when we deployed a Smart Contract to Ethereum, Polygon,... networks).
- lock script for an account can be inferenced from the privateKey
```
private key
  → public key (secp256k1 elliptic curve multiplication)
  → blake160(pubkey) = 20 bytes
  → lockScript { code_hash: Secp256k1Blake160, args: blake160(pubkey) }
```
- The `ccc` package contains KnownScript which is the deployed scripts on the chain (includes both system scripts and well-known scripts)

> E.g: When we develop with xUDT, we can easily get the xUDT configs by `ccc.KnownScript.XUdt`. It can be considered as a convenience alias. 
- While the "lock" script run on the input cell(s) to manage "who is able to consume the cell(s)?", the "type" script run on both input and output cell(s) to control "what rules must this cell follow?" when cell(s) were destructed or created.

### xUDT token
- In CKB, token doesn't exist in contract state like ERC-20, it exists in cells.
- `xUDTargs` includes 2 parts:
```
xudtArgs = owner_lock_hash (32 bytes = 64 hex chars)
         + flags (4 bytes = 8 hex chars)
```

`xUDTargs` is a reference to a deployed token, and answers for questions: "who has deployed it?", "what's its extension?"

- The last 8 hex chars support advanced features (deepdive later). In the example DApp, we are learning the pure xUDT without extension (all 8 hex chars are zero)
- Because xUDT separated tokens by xUDTArgs (= owner_lock_hash + flags), and owner_lock_hash is a fixed value for each private key. It means, with 1 account, there's no similar token with the same flags extension can be existed. We are only able to change token logic through flags.
- If we develop ERC-20 token in Ethereum, we usually use inherit codebase to create new ERC-20 tokens. They are separated by contract address (totally different from CKB xUDT). It means, with 1 account, we can deploy unlimited ERC-20 contracts.
- xUDT were not stored in contract state, it was stored on cells. These xUDT cells are linked to the xUDT contract. We don't create a new contract, we used the existing codebase logic and utilize it.
