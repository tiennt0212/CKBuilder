My last week of the bootcamp, and the densest one: five branches landed on `canary`, taking
CKBuilder from "a few pages that work on my machine" to an application with a public address,
one that explains its own failures, and that carries a roadmap someone else can read.

## Completed

### Wrote the first smart contract and ran it for real on chain

CKBuilder already had a page for deploying scripts, but no contract of *ours* had ever run a
full lifecycle. Now one has. A small Rust contract called `counter` — its entire rule is one
sentence, "the new value must equal the old value plus one" — compiled to RISC-V, covered by 6
automated tests, deployed to a devnet, then created, incremented and destroyed through the UI
with a real MetaMask wallet. This is the first time the loop *write a contract → deploy it →
use it* closed inside this project.

`/counter` was redesigned as a table of tracked counters plus an action dialog: each counter is
a row, and clicking one opens a form beside a live preview of the transaction about to be
signed. The layout exists so a learner sees the state *before* and *after* side by side, which
is exactly what this contract teaches.

Building it also exposed a shaky foundation that had to be fixed first. The app had **two
places both claiming to be the source of truth** for which network was active — one owned by
the wallet library, one a store that built its own client and pushed it back the other way. The
two were never synchronised, so every page reload was a race over which side won, occasionally
dropping the wallet connection. I collapsed it to a single source, and folded in the wallet
account state that had been duplicated across two files. None of this is visible in the UI, but
every feature that followed stands on it.

### Issuing and transferring tokens — the `/tokens` page

`/tokens` went from a placeholder with a name to a page that does three things: issue a token
under the xUDT standard, show its balance, and transfer it to another address. All of it ran on
a real devnet, and I opened the resulting transactions to check them field by field rather than
stopping at "it compiles": the token that came out is genuinely the one my wallet is authorised
to mint, the amount is stored in the right format, and very large numbers — past JavaScript's
safe integer range — survive the form intact.

Two findings are worth recording because they run against intuition. First, **the cost of
holding a token is not a fixed number** — it depends on the kind of wallet the user has, 146 or
148 CKB. I had written that rule into the documentation myself and still hardcoded "146" into
three pieces of display text, which took two separate commits to undo. Second, **a transfer
usually needs no new CKB at all**: the storage attached to the old token cells carries forward
into the new ones. That is only true under CKB's cell model, and is wrong under the familiar
account-balance picture.

Two things I deliberately did *not* build: the page doesn't read a token's name or symbol
(those live in a separate data cell, split out into its own issue), and it doesn't keep a local
list of tokens — a token's identity is always derivable from chain, so a local copy would just
be a second source of truth waiting to drift.

### When a transaction is rejected, the app explains instead of dumping raw text

CKBuilder had already treated "the node rejected this" as a legitimate outcome to display
rather than an error to hide. But that rejection reached the screen as the node's raw technical
wording — accurate, and close to meaningless for someone learning.

This week I added a decoder. It reads the node's answer and restates it as *what happened, why,
and what to do next*, keeping the original wording underneath, collapsed, for anyone who wants
it. The part I care about most: **two failures that each cost me a full debugging session in
earlier weeks are now things the app says out loud** — the mismatched deploy configuration that
makes a script permanently unresolvable, and a binary compiled with an option CKB's virtual
machine will not execute. Personal experience turned into something the next person doesn't pay
for again.

One principle I held firmly: **the meaning of an error code belongs to the contract, and there
is no global lookup table**. Each contract defines its own numbers, so reading one contract's
code through another's table would be a confident lie. `/counter` knows its own contract and
translates the number into a sentence; `/invoke` runs arbitrary scripts and therefore
deliberately does *not* guess — it shows the bare number and says plainly that its meaning is
defined by the contract.

Alongside this I added **automated tests for the JavaScript side**, which the project had never
had (only the Rust side was covered). The reason is specific: the error decoder is the kind of
code that fails *silently* — an unmatched rejection falls back to "unknown", which looks fine
while teaching nothing. There are now 99 tests running in just over a second, and I kept the
mandatory scope deliberately narrow: only the pure logic layer requires a test. Extending it
across the whole app would turn a learning project into a testing programme.

And manual use still caught what automation could not: clicking *reject* on the MetaMask prompt
displayed the literal text `[object Object]` as the entire explanation. The cause is that every
browser wallet reports errors in a shape different from what I had assumed — the information
was there all along, discarded one branch too early.

### The app is publicly reachable, and the unbuilt pages tell the truth

This strand added no CKB capability. It closed the gap between "six pages work" and "someone
else can tell that six pages work".

CKBuilder now **runs publicly on testnet** at `ck-builder-s1eo.vercel.app` — nothing to
install, connect a wallet and use it. It ships with a README carrying a per-page status table,
six screenshots taken against real chain data, and an explanation of why the app deliberately
runs entirely in the browser.

The five unbuilt pages used to show an amber warning reading "Connect your wallet to get
started" — blaming the wallet, on pages that have nothing to do with the wallet. Each now says
directly which milestone it belongs to and which issue tracks it. In the same spirit, I
**downgraded `/invoke` to "unverified"** in the README myself: it builds and broadcasts
transactions, but the only script ever driven through it was rejected by the virtual machine
for an unrelated reason, so the page's own correctness remains unproven. Better to write that
than to leave a green check with nothing behind it.

A small detail, but exactly the class of bug that only appears once something is public: a
devnet node runs locally over an unencrypted connection, and browsers block an HTTPS page from
reaching it. On the deployed build, choosing "Local Devnet" produced a state where every call
failed in silence. That option is now disabled, with the reason shown in place of the URL.

### A context layer for the AI agent, shaped around the development roadmap

I built most of this project alongside an AI agent, and the `CLAUDE.md` instruction file had
grown to nearly 300 lines — simply because I wanted to apply a fuller context set, better
matched to the roadmap ahead, based on my own experience working with agents. This week I
reorganised it into the right shape: a short index on the outside, and beneath it context
layers split by purpose — system architecture, the CKB terms this repo uses in a narrow sense,
a ledger of traps already hit (26 entries, each pointing at the exact line of code), a
decisions log (16 entries, plus 8 questions left open), and the definition of done.

The benefit is twofold. The agent reads only the layer relevant to the task instead of paying
for all of it every session. More importantly, what I learned now **stays in the repository**
rather than staying in my head — every entry cites its source, so the next person can re-verify
it, or delete it once the code has moved on. While reorganising, I also found several
descriptions that had drifted from the actual code and corrected them; the most consequential
was one architectural claim wrong enough to send an agent building a server-side component this
application fundamentally cannot have.

### The roadmap re-cut around the product rather than around lessons

The roadmap had been organised as 32 issues named "Course 01… Course 24", tracking the
syllabus. That is tidy for studying and awkward for managing delivery: one lesson can spread
across three pages, three lessons can collapse into one page, so the board never answered the
question "what ships this week?".

I re-cut it around product capability: **7 milestone groups** — the bootcamp demo (due August
14th), assets, custom locks, infrastructure, advanced, production, and platform / developer
experience. The near milestone is broken down to items that can be picked up immediately; the
distant ones deliberately stop at outline level rather than inventing detail before the
information exists. The change paid off immediately: the demo milestone closed 11 of 14 items
in three days, and what remains is now visibly "not yet enough known to plan" rather than "not
yet done".

## State at the end of the bootcamp

**Working today**: six pages build and broadcast real transactions — CKB transfer, cell
explorer, script deploy, the registry of deployed scripts, counter, and xUDT tokens. Live on
testnet. Two Rust contracts compile, of which `counter` is tested and has run a full lifecycle.

**Bootcamp demo milestone (due August 14th): 11 closed / 3 open** — only the transaction
history page `/history` and its two sub-items remain. This is the closest thing to a finish
line for anyone wanting to close the milestone on time.

**33 issues remain open**, all grouped by milestone and carrying their technical constraints in
the body rather than only in the title. Three worth reading first:

- **The architecture of `/invoke`** — the largest decision still open. The page can currently
  build exactly *one* transaction shape, and it does not generalise. The full analysis is
  written into the issue, with the evidence already present in the repo: both the counter
  contract and xUDT had to hand-write their own builders because neither could be expressed
  through the shared template.
- **A crash when building transactions on devnet** — it blocks local testing outright, so it
  deserves attention early because it stands in front of everything else.
- **No CI** — build, lint and tests are still run by hand before each PR.

**Technical debt I recorded rather than hid**: `/invoke` still carries the *unverified* label;
the hash-lock contract needs recompiling with a different option before CKB's VM will run it;
the error decoder has been matched against real node output but does not yet cover every kind
of rejection; and the selected network is not remembered across a page reload.

## Key Learnings

### On CKB, an action lives in the *shape* of the transaction, not in calldata
This took the longest to see clearly, and it runs through `/invoke`, `/counter` and `/tokens`
alike. On Ethereum, missing a contract's interface description costs you *labels* — you can
still call the function. On CKB, missing it means **not knowing what shape the transaction must
have**, which is a different order of problem. The consequence is concrete: an action list can
never be derived from a script's identifier. The rule "an update needs exactly one input and
one output" exists in Rust source, not on chain — a human has to read it and hand-write the
builder. Any idea along the lines of "a form that generates itself for an arbitrary script"
has to start from there.

### Failures always surface far from where they were caused
A script that cannot be found, because of a mismatched pair chosen on the deploy page. The VM
reporting an invalid instruction, because of a compiler flag. A cell silently underfunded,
because one argument was omitted. None of these point at where they were created. What I take
from it is that **you have to identify the right layer before reaching for a fix**: some errors
can be blocked at the form (couple the two controls together), others cannot — a binary has to
be recompiled, so no UI change saves you and what's needed is a check at deploy time. What is
always worth building is the decoder and the gotchas ledger citing exact lines, so that next
time the error names its own location.

### Running it for real still catches what automation misses
The three most serious bugs this week — the `[object Object]` message, the wrong capacity
figure, and an error code the library parsed incorrectly — all came out of **using a real
wallet against a real network**, not from tests or the type checker. Conversely, the layer that
genuinely *deserves* automated tests is the pure logic layer: it fails silently, invisible to
the eye. Testing the right layer matters more than testing a lot.

### Agent context is part of the roadmap, not a side document
Twelve weeks of working alongside an agent showed me output quality depends directly on the
quality of the context loaded — and context has to be *designed* against the development
roadmap, then maintained like code: split by purpose, every claim citing a source that can be
re-verified, and anything whose reason nobody remembers listed as an open question rather than
given an invented one. A description that has drifted from the code costs more than no
description at all, because the agent believes it and builds in the wrong direction.

### How you track progress has to match what gets delivered, not what gets learned
A syllabus-shaped roadmap looks tidy and cannot answer the question that matters most — what
ships this week. Regrouping by product capability, putting a deadline on exactly one near
milestone and leaving the distant ones as outlines, made the real scope visible instead of
guessed at. This continues the lesson from week 10 about splitting the definition of done into
two tiers: **process cost has to be weighed like a feature**, because it draws on the same
budget of time.

### Write the gap where people will actually read it
What kept this project from fooling itself over twelve weeks was the habit of recording the
gaps in the **README and in PR descriptions**, not in private notes: `/invoke` carries the
*unverified* label on the public README; the error-decoder PR stated "not yet tested against a
real rejection on testnet" right before merge; the counter PR stated that the docs and the
design artboard had diverged. "Merged" is not the same claim as "done" — and the only place
that keeps the difference from being forgotten is the place the next person is certain to open.
